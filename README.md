# kseniakostina.ru

Одностраничный сайт. Обычная статика: HTML + CSS + один файл JS. Ни сборки,
ни зависимостей, ни внешних запросов — папку можно положить в GitHub Pages
как есть.

## Структура

```
index.html                 разметка, мета-теги, Schema.org
assets/css/styles.css      токены, шрифты, компоненты, адаптив
assets/js/app.js           появление блоков, FAQ, счётчики, параллакс, меню
assets/fonts/*.woff2       Playfair Display (600) + Montserrat (3 сабсета)
assets/img/*.webp          изображения, с вариантами под мобильные
assets/img/og-image.jpg    превью для Telegram и соцсетей (1200×630)
robots.txt, sitemap.xml    для поисковиков
_headers                   заголовки для Cloudflare Pages (см. ниже)
.nojekyll                  отключает обработку Jekyll на GitHub Pages
```

## Как всё устроено

**Стилей в разметке нет.** Всё оформление — в `styles.css`, на классах.
Поэтому в адаптиве не понадобилось ни одного `!important`: переопределять
инлайновые стили больше не нужно.

**Мобильный порядок блоков держат классы,** а не позиции элементов. Раньше
было `#heroText > div:nth-child(1) { order:1 }` — вставили один `<div>` и
раскладка поехала. Теперь у каждого блока свой класс (`.hero__eyebrow`,
`.about__media` и так далее), и порядок от структуры не зависит.

**Один слушатель прокрутки на всю страницу.** Внутри кадра сначала идут все
измерения, потом все записи стилей — иначе браузер пересчитывает раскладку
по нескольку раз за кадр, и на телефоне это чувствуется. Базовый масштаб
параллакса лежит в CSS, JS подставляет только смещение через переменные
`--plx-y` и `--gem-scale`.

**Уважение к настройкам системы.** Если у посетителя включена экономия
движения, выключаются появление блоков, перелив фона, анимация гармошки,
параллакс и счётчики. Это и CSS-медиазапрос, и та же проверка в JS.

**Доступность.** Бургер — настоящая `<button>` с `aria-expanded`, меню
закрывается по Escape. FAQ переключает настоящий атрибут `open`, поэтому
скринридер и поисковик видят то же состояние, что и зрячий посетитель.
Есть видимый фокус с клавиатуры.

**Без JS страница остаётся читаемой:** текст виден весь, FAQ работает
штатным поведением `<details>`. Скрытыми блоки становятся только если JS
включён — это делает однострочный скрипт в `<head>`.

## Что важно знать при правках

**Веса Montserrat.** Начертания 400, 500 и 600 намеренно ссылаются на один
и тот же файл Regular — ровно как было в исходном бандле, чтобы вид не
изменился. Текст с `font-weight:500/600` рисуется обычным Regular. Настоящие
Medium и SemiBold — это два дополнительных файла и правка `@font-face`.

**Картинки** только в WebP, без запасных JPEG/PNG. Поддержка — все браузеры
с 2020 года. У крупных фото есть уменьшенные варианты (`-640`, `-720`,
`-800`, `-480`, `-208`), подключённые через `srcset`/`sizes`. Если меняете
картинку — пересоберите варианты и обновите `width`/`height` в `index.html`,
иначе вернутся скачки вёрстки при загрузке.

**CSP привязана к хешу.** В `index.html` есть один инлайновый скрипт
(`document.documentElement.classList.add('js')`), и его sha256 прописан в
`Content-Security-Policy` и в `_headers`. Измените этот скрипт хоть на
символ — пересчитайте хеш в обоих местах, иначе браузер его заблокирует:

```bash
printf "%s" "document.documentElement.classList.add('js')" | openssl dgst -sha256 -binary | openssl base64
```

**Адрес сайта** прописан в четырёх местах: `<link rel="canonical">`,
`og:url`, блок Schema.org в `index.html` и `sitemap.xml`. При переезде на
`kseniakostina.ru` поменять во всех.

## Про заголовки и защиту от вложения в чужой iframe

GitHub Pages не позволяет задавать HTTP-заголовки, поэтому политика
безопасности продублирована в `<meta>` внутри `index.html`. Работает всё,
кроме `frame-ancestors` — эту директиву браузеры в `<meta>` игнорируют по
спецификации. То есть на GitHub Pages сайт по-прежнему можно вложить в
iframe на чужом домене.

Полноценно закрывается это только настоящим заголовком. Файл `_headers`
уже готов: на Cloudflare Pages или Netlify он подхватится сам и добавит
`frame-ancestors 'none'`, `X-Content-Type-Options`, `Permissions-Policy`
и долгий кэш для картинок и шрифтов. GitHub Pages этот файл просто
игнорирует.

**Про хеши в именах файлов.** Их намеренно нет. Они нужны, чтобы вечно
кэшировать неизменяемые файлы, а GitHub Pages жёстко отдаёт
`Cache-Control: max-age=600` и переопределить это нельзя — выигрыша не
будет, а редактировать имена вручную станет неудобно. Если сайт переедет
на Cloudflare Pages, кэш уже настроен в `_headers`, и вот тогда хеши
имеет смысл добавить.

## Что осталось за рамками

Настоящие Medium/SemiBold для Montserrat (см. выше) и `robots.txt` —
на проектном адресе `*.github.io/kseniakostina/` поисковики читают
`robots.txt` только из корня домена, так что здесь он начнёт работать
после переезда на собственный домен. `sitemap.xml` можно скормить
Search Console напрямую, он работает с любого пути.

## Каталог и калькулятор

Две отдельные страницы: `catalog/` и `calculator/`. Бэкенда нет — данные
лежат рядом в JSON, вся логика в браузере.

### Каталог — откуда берутся позиции

Источник — канал-витрина [@diamondbabecloset](https://t.me/diamondbabecloset).
Ксения публикует посты как привыкла, менять в её работе ничего не нужно.

```bash
python3 tools/parse_telegram.py "Messages_Ювелирный Гардероб.csv"
```

Скрипт разбирает выгрузку и пишет `assets/data/catalog.json`. На текущей
выгрузке: 401 позиция, 159 в наличии. Камень распознаётся в 98% постов,
цена в 97%, вес в 91%, огранка в 45%. Низкое покрытие по огранке —
следствие непроставленных хештегов, а не ошибок разбора.

**Вид изделия многозначен.** У позиции есть основной `type` (для карточки)
и список `types` (для фильтра). Обычно они совпадают. Два исключения:

* **Сет** — пост с двумя и более видами изделия (`#Пусеты #Подвески`).
  Основной тип — «Сет», а в `types` он попадает и как «Сет», и как каждая
  своя составляющая, поэтому находится по любому из фильтров. Иначе сет
  пришлось бы прятать под один вид: раньше комплект «пусеты + подвеска»
  показывался только в «Подвесках».
* **Отдельный камень** — пост без тега-изделия. Это сам камень на продажу,
  а не украшение. В фильтре — отдельной кнопкой, в подписи карточки не
  повторяется (заголовок и так камень).

«Сет» и «Отдельный камень» в ряду фильтров всегда последние: это не виды
украшений, а особые корзины.

**Ручные исправления.** Не правьте `catalog.json` — он перезаписывается при
следующем разборе. Создайте `assets/data/overrides.json` с массивом правок,
они накладываются поверх автоматики:

```json
[{ "id": 434, "price": 3350, "type": "Теннисный браслет", "cut": "Круг" }]
```

Скрипт печатает список позиций на проверку. Почти все они — посты, где в
одном сообщении сразу несколько изделий (например пять браслетов разного
веса). Автоматика берёт первую цену и помечает такой пост.

**Фотографии.** Обложки карточек — кадр из видео поста. В канале камень
почти всегда снят вертикальным роликом (крутят в руке под лампой), и один
резкий кадр из середины — готовая обложка. Собираются из отдельной выгрузки
канала в формате JSON (Telegram Desktop → Export chat history → Machine-readable
JSON, галки Photos и Videos, Size limit на максимум — иначе видео не влезут):

```bash
python3 tools/covers_from_export.py "<папка выгрузки>"
python3 tools/parse_telegram.py "Messages_Ювелирный Гардероб.csv"
```

Первый скрипт кладёт `assets/stock/<id>.webp` (id поста = id позиции), второй
пересобирает каталог — он подхватывает обложки по имени файла. Из нескольких
кадров середины ролика берётся самый резкий (дисперсия Лапласиана): половина
кадров смазана движением. Кадр обрезается в квадрат.

Выгрузку по датам можно делать частями и складывать в одну папку —
существующие обложки скрипт не перезаписывает (ключ `--force` пересобирает
всё). У кого поста нет в выгрузке — остаётся заглушка, окрашенная по камню.
Сейчас собраны обложки за июнь–июль 2026 (75 позиций); остальным нужна
выгрузка за более ранние даты.

### Калькулятор — откуда берутся цены

`assets/data/pricing.json` — таблицы из печатного каталога 2026 года.
Обновляются вручную примерно раз в квартал.

Между табличными точками — линейная интерполяция. За границами таблиц
намеренно **не** экстраполируем: там слишком многое зависит от конкретного
камня, и выдуманная цифра подорвала бы доверие к остальным. Вместо неё
показывается «рассчитаем индивидуально» и переход в личку.

Характеристики камня можно не выбирать: вариант «Любое» показывает вилку
между двумя качествами из таблицы. Это настоящая вилка по данным, а не
придуманный разброс вокруг одной цифры. Расшифровка показывается одна —
к выбранной кнопке; тексты в `GRADE_NOTE` в `assets/js/calculator.js`.

**Кольца выбираются по трём осям** — подтип (солитер / в обсыпке /
дорожка), огранка (круглая / фантазийная) и цвет камня (белый / жёлтый).
Оси задаются полями `family`, `cut_name` и `color_name` в `pricing.json`,
список осей — в `AXES` в `assets/js/calculator.js`. Ряд показывается,
только когда при уже сделанном выборе на этой оси есть из чего выбирать:
у дорожки одна огранка, у круглых бриллиантов один цвет. Там, где осей
в данных нет, остаётся один ряд кнопок с названиями вариантов: у пусет
«жёлтые бриллианты» — это не огранка, и осей из этого не выходит.

**Двойная вилка у жёлтых колец разобрана.** На странице 20 каталога цена
солитера записана через дробь: для Y-Z 1 карат — `1 400–1 800 $ /
3 600–4 400 $`. В калькулятор взята **вторая** вилка. Основание: таблица
«в обсыпке» с одной вилкой отличается от второй вилки солитера ровно на
1 250 $ во всех двадцати строках, по обоим концам. У белых бриллиантов
(страница 22) обсыпка так же ровно на 600 $ дороже солитера, и там числа
заведомо за изделие целиком. Значит вторая вилка — тоже изделие целиком,
а первая, судя по всему, стоимость самого камня.

Это вывод из арифметики, а не слова Ксении. Подтвердить у неё стоит —
вопрос короткий: «вторая цифра в паре — это цена готового кольца?»

**Тексты страницы — из печатного каталога 2026 и канала Ксении.**
Часть формулировок дословная (оговорка под расчётом, блоки 4C,
сертификации и порядка заказа). Переписывать их своими словами не надо:
это её голос, и он убедительнее любой обработки.

Диаметр круглого бриллианта считается как `6.5 × ct^(1/3)` — опорная точка
1 ct = 6,5 мм из её же каталога. Проверено по остальным точкам таблицы
соответствия (0,35 ct → 4,5 мм, 0,5 ct → 5 мм).

### Картинки калькулятора

```bash
python3 tools/prepare_images.py            # источник: ../pdf по умолчанию
```

Источник — папка `website_diamonds/pdf` (выгрузка печатного каталога,
рядом лежит `_манифест.md` с описанием всех файлов). Скрипт кладёт
результат в `assets/img/cuts` и печатает размер каждой картинки —
эти же числа должны стоять в `width`/`height` разметки, иначе вёрстка
скачет при загрузке.

Что генерируется:

* `item-<id>.webp` — фото изделия под каждый вариант из `pricing.json`.
  Привязка «вариант → исходник» в словаре `PRODUCTS` внутри скрипта.
* `size-<изделие>.webp` — схема размеров бриллиантов на руке, ухе,
  запястье, шее.
* `edu-carat / edu-cut / edu-color / edu-clarity` — четыре
  характеристики 4C для нижнего блока страницы.

Фон определяется автоматически: снимки на белом обрезаются по краям,
снимки на чёрном вырезаются заливкой от границ (тёмные грани внутри
камня при этом остаются) и кладутся на белый.

**Пропорции фото изделий не выравниваются.** Исходники — групповые
кадры («одно и то же кольцо в трёх цветах золота»), и у половины из них
соотношение сторон вроде 4:1. Раньше их вписывали в квадрат, и три
четверти карточки занимало пустое белое поле. Теперь каждый кадр
обрезается по самому изделию и сохраняет свои пропорции — а значит,
у каждого свои `width`/`height`. Скрипт печатает размеры, эти же числа
стоят в словаре `ITEM_BOX` в `assets/js/calculator.js`. Не обновите —
вёрстка будет скакать при переключении исполнения. То же самое
у схем размеров: словарь `SIZE_REF` там же.

Диаграмм огранок и тёмных плиток больше нет — калькулятор показывает
только фотографию изделия. Общего кадра всех форм огранки под
фантазийные варианты тоже больше нет: у них появились собственные
групповые снимки.

### Что осталось за рамками

* Отдельные адреса вида `/catalog/1234` с разметкой Product — пока у позиций
  нет фотографий, отдельные страницы дадут мало.
* Формы заявок: продажи остаются в Telegram, кнопка копирует заготовку
  запроса и открывает диалог. Подставить текст в личное сообщение ссылкой
  Telegram не позволяет.
* Английская версия.


## Открытые вопросы

* **Обложки не на весь каталог.** Собраны за июнь–июль 2026 (75 позиций),
  у остальных — заглушка по цвету камня. Чтобы закрыть весь каталог, нужна
  выгрузка канала за более ранние даты (см. «Фотографии» выше).
* **Расшифровка второй вилки у жёлтых колец** держится на арифметике,
  а не на словах Ксении (разбор — выше, в разделе про калькулятор).
  Цены уже опубликованы, так что подтвердить стоит не откладывая.
* **Состояние «вес за таблицами» не показывается.** Тексты для него
  написаны, но границы ползунка равны крайним строкам таблицы, поэтому
  выйти за них мышью нельзя. Чтобы состояние заработало, ползунок надо
  расширить за табличные точки — например, у колец до 5 ct. Это решение
  о продукте, а не о вёрстке: вопрос в том, хотим ли мы вести разговор
  про камни крупнее каталожных.
* **Отдельные адреса позиций** `/catalog/1234` со Schema.org Product
  не сделаны: пока у позиций нет фотографий, толку от них мало.
* **Английская версия** — значительная часть клиентов в ОАЭ.

## Как это опубликовано

Папка — клон `github.com/shbshv-czec/kseniakostina`, ветка `main`,
GitHub Pages отдаёт `https://shbshv-czec.github.io/kseniakostina/`.
Правки публикуются обычным `git push`; `gh` установлен и авторизован.

Каталог и калькулятор **убраны из меню** сайта: они открываются только
по прямой ссылке `/catalog/` и `/calculator/`.
